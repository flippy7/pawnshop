# Конституція проєкту «Ломбард»

## Основні принципи

### I. Мінімальна складність рішень

Архітектура та код ПОВИННІ використовувати найпростіші рішення, достатні для поточних
навчальних вимог. Заборонено додавати рівні абстракції, шаблони проєктування, бібліотеки
або інфраструктуру без конкретної потреби, зафіксованої у специфікації чи плані.
Кожне ускладнення ПОВИННО мати пояснення, чому простіше рішення не задовольняє вимогу.
Це зберігає зрозумілість навчального прикладу та полегшує його пояснення.

### II. Єдина відповідальність класу (SRP)

Кожен клас ПОВИНЕН мати одну чітко визначену відповідальність і одну причину для зміни.
Опис призначення класу ПОВИНЕН пояснювати цю відповідальність. Клас НЕ ПОВИНЕН
одночасно містити правила предметної області, керувати консольним інтерфейсом
та імітувати незалежні зовнішні операції. Якщо клас поєднує незалежні обов'язки,
їх ПОВИННО бути розділено між відповідними класами без зайвих рівнів абстракції.

### III. Імітація зовнішніх операцій у консолі

Методи, що представляють зовнішні операції, ПОВИННІ виводити зрозуміле повідомлення
в консоль із назвою дії та даними, потрібними для демонстрації сценарію.
Реальні платежі, надсилання повідомлень, звернення до мережевих API та інші зовнішні
операції заборонені. Обчислення, перевірки та зміни стану об'єктів у пам'яті
ПОВИННІ виконуватися згідно зі специфікацією; консольне повідомлення замінює саме
зовнішню дію. Це дає змогу демонструвати поведінку без зовнішньої інфраструктури.

### IV. Компіляція та запуск із командного рядка

Застосунок ПОВИНЕН компілюватися та запускатися виключно командами `javac` і `java`
з командного рядка. Інструкція запуску ПОВИННА містити потрібну версію JDK,
робочий каталог і точні команди. Компіляція та виконання НЕ ПОВИННІ залежати від IDE,
зовнішніх сервісів, мережевого доступу або баз даних. Дані навчальних сценаріїв
ПОВИННІ зберігатися в пам'яті застосунку; підключення до баз даних заборонене.

### V. Явне впровадження залежностей

Dependency Injection ПОВИННО здійснюватися лише через конструктори або setter-методи.
Залежності ПОВИННІ передаватися ззовні об'єкта, який їх використовує.
Статичні методи впровадження залежностей, глобальні реєстри залежностей
і прихований пошук залежностей заборонені. Метод `main` може створювати об'єкти
та передавати їх конструкторам або setter-методам, але НЕ ПОВИНЕН виконувати роль
статичного постачальника залежностей. Об'єкт НЕ ПОВИНЕН виконувати операцію,
доки потрібну для неї залежність не передано.

### VI. Мова імен та пояснень

Назви класів, методів та атрибутів ПОВИННІ бути англійською мовою.
Назви класів ПОВИННІ використовувати `PascalCase`, методів та атрибутів — `camelCase`,
констант — `UPPER_SNAKE_CASE`. Коментарі в коді, документація JavaDoc та пояснення
ПОВИННІ бути українською мовою. Англомовні ідентифікатори, назви API та команди
в українському тексті ПОВИННІ зберігати своє оригінальне написання.

### VII. Текстові UML-діаграми в каталозі docs

UML-діаграми ПОВИННІ зберігатися в каталозі `docs/` або його підкаталогах
у текстовому форматі, наприклад PlantUML (`.puml`) чи Mermaid (`.mmd`).
Зображення діаграми НЕ МОЖЕ бути єдиним джерелом її опису.
Діаграми ПОВИННІ відповідати актуальним класам, їхнім відповідальностям і зв'язкам;
зміни, що впливають на ці елементи, ПОВИННІ супроводжуватися оновленням діаграм.
Текстове джерело робить зміни доступними для перегляду у системі контролю версій.

### VIII. Специфікація українською мовою

Специфікація проєкту, включно з вимогами, користувацькими сценаріями,
критеріями приймання, планами та описами завдань, ПОВИННА вестися українською мовою.
Терміни предметної області «Ломбард» ПОВИННІ використовуватися послідовно
в усіх документах. Ідентифікатори коду, шляхи, команди та назви технологій
ПОВИННІ зберігати оригінальне написання для однозначного зіставлення з реалізацією.

## Технічні обмеження

Проєкт є навчальним Java-застосунком для інформаційної системи предметної області
«Ломбард». Реалізація ПОВИННА спиратися на стандартну бібліотеку JDK.
Фреймворки впровадження залежностей, сервери застосунків та бібліотеки доступу
до баз даних заборонені: вони суперечать вимогам простоти та автономного запуску.
Набір функцій і правила предметної області ПОВИННІ визначатися специфікацією;
ця конституція встановлює обов'язкові обмеження для їх проєктування та реалізації.

## Порядок розроблення та перевірки

Перед реалізацією зміни ПОВИННІ бути визначені її вимога, відповідальності класів
і спосіб передавання залежностей. План та завдання ПОВИННІ перевірятися
на відповідність усім восьми принципам.

Перед прийняттям зміни ПОВИННО бути перевірено:

- Компіляцію та запуск із командного рядка за задокументованими командами.
- Виконання відповідного навчального сценарію та повідомлення про зовнішні операції.
- Єдину відповідальність класів і впровадження залежностей через конструктори чи setter-методи.
- Відсутність реальних зовнішніх операцій, сервісів і баз даних.
- Відповідність імен, коментарів, специфікації та UML-діаграм мовним і файловим вимогам.

Результат перевірки ПОВИНЕН містити виконані команди та фактично спостережений результат.
Для змін лише документації достатньо перевірити зміст, мову та узгодженість документів;
повторна компіляція потрібна лише за зміни коду або команд компіляції чи запуску.

## Управління конституцією

Ця конституція має пріоритет над іншими проєктними документами щодо принципів
розроблення. Специфікації, плани, завдання, код і діаграми ПОВИННІ їй відповідати.
Виявлену невідповідність ПОВИННО бути усунено до прийняття зміни.

Поправка ПОВИННА містити причину, точний опис змінених правил та перелік
документів або частин реалізації, які потребують узгодження. Поправки затверджує
відповідальний за проєкт через прийняття зміни до конституції в системі контролю версій.
Одночасно ПОВИННІ оновлюватися версія, дата останньої зміни та звіт про вплив змін.
Дата первинного ухвалення ПОВИННА залишатися незмінною.

Версія ПОВИННА відповідати формату `MAJOR.MINOR.PATCH`:

- `MAJOR` збільшується при вилученні або несумісному перевизначенні принципів чи правил.
- `MINOR` збільшується при додаванні принципу, розділу або суттєвому розширенні вимог.
- `PATCH` збільшується при уточненнях і виправленнях, що не змінюють змісту вимог.

Під час кожного перегляду специфікації, плану чи змін реалізації ПОВИННА
перевірятися відповідність конституції. Відступ від принципу потребує попереднього
внесення та затвердження відповідної поправки до конституції.
