# Дослідження та рішення: задача 001

**Дата**: 2026-11-15. Джерела вимог: spec.md і конституція v1.0.0.
Невідомі щодо формату, моделі й перевірки вирішено нижче.

## 1. Спосіб підготовки

**Рішення**: текст діаграм готувати безпосередньо за спільною моделлю; для CRC використати
допоміжний Python з openpyxl. Універсальний генератор не створювати.
**Обґрунтування**: п'ять невеликих фіксованих документів не виправдовують окрему архітектуру.
**Альтернативи**: генератор із власною схемою даних додає зайвий рівень;
ручний запис OOXML ZIP додає складність; CSV не задовольняє вимогу XLSX.

## 2. Синтаксис діаграм

**Рішення**: PlantUML для ролей і use case; Mermaid classDiagram, sequenceDiagram,
stateDiagram-v2 для решти. Українські підписи відокремлювати від англійських ідентифікаторів.
**Обґрунтування**: це задані формати; офіційні описи підтверджують потрібні елементи.
**Альтернативи**: єдиний формат або зображення без текстового джерела суперечать вимогам.
Джерела: [PlantUML use case](https://plantuml.com/use-case-diagram),
[Mermaid class](https://mermaid.js.org/syntax/classDiagram.html),
[Mermaid sequence](https://mermaid.js.org/syntax/sequenceDiagram.html),
[Mermaid state](https://mermaid.js.org/syntax/stateDiagram.html).

## 3. final, override та конструктори

**Рішення**: конструктори показувати операціями з іменем класу без типу результату;
final getId та перевизначення getRole пояснювати видимими українськими примітками
з точними сигнатурами. Перевантаження appraise показувати двома операціями.
**Обґрунтування**: Mermaid документує спеціальні позначення abstract/static;
окремий спеціальний маркер Java final/Override не припускається. Це висновок
із [опису членів і приміток Mermaid](https://mermaid.js.org/syntax/classDiagram.html).
**Альтернативи**: вигаданий суфікс може зламати синтаксис; лише прихований коментар
не дозволить перевірити вимогу на відображеній діаграмі.

## 4. SOLID і володіння

**Рішення**: Appraiser реалізує ICollateralAppraisal; StolenItemCheckService реалізує
IStolenItemCheck. LoanAgreement отримує контракт перевірки через конструктор.
Композиція стосується об'єкта застави в договорі; викуп не знищує фізичну річ.
**Обґрунтування**: це реалізує припущення специфікації та DIP без статичних фабрик.
**Альтернативи**: пряме створення сервісу всередині договору порушує DI;
винесення кожної операції в новий клас невиправдано ускладнює модель.

## 5. Макет CRC та перевірка

**Рішення**: 9 аркушів, по одному на тип, назва аркуша збігається з типом.
Workbook.save створює книгу, load_workbook перевіряє повторне читання.
**Обґрунтування**: це простий підтримуваний спосіб роботи з XLSX за
[офіційною документацією openpyxl](https://openpyxl.readthedocs.io/en/stable/tutorial.html).
**Альтернативи**: дев'ять окремих файлів не відповідають єдиному кінцевому шляху;
автоматизація Excel не потрібна для створення книги без формул.

## 6. Межі середовища

**Рішення**: перевіряти локальними засобами, без онлайн-редакторів і зовнішніх API.
Встановлення відсутніх інструментів виконувати лише під час реалізації,
зафіксувавши фактичні версії. План не стверджує, що відображення вже перевірено.
**Альтернативи**: Java-бібліотека для XLSX додала б непотрібну залежність до застосунку.
