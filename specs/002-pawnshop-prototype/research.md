# Дослідження технічних рішень

**Дата**: 2026-11-15 · **Задача**: 002. Рішення для планування ухвалені.

Джерела: spec.md задачі 002, конституція 1.0.0 та всі п'ять документів docs. Виконано локальне дослідження й незалежний огляд агентом. Код і експериментальні запуски Java на цьому етапі відсутні.

## 1. Платформа та структура

- **Рішення**: Java 17, один пакет pawnshop, дев'ять модельних типів і Main, лише JDK, javac/java.
- **Обґрунтування**: конкретна базова версія робить запуск відтворюваним; стандартних типів достатньо. Додаткові шари для фіксованих прикладів не потрібні.
- **Розглянуті альтернативи**: Maven/Gradle, Spring, БД суперечать автономності та простоті; кілька пакетів не дають необхідної переваги.

## 2. Грошові значення

- **Рішення**: BigDecimal із десяткових рядків. До зміни даних перевіряти null, знак і можливість `setScale(2, RoundingMode.UNNECESSARY)`; порівнювати через compareTo.
- **Обґрунтування**: 840, 840.01 і 840.000 приймаються за точністю; 840.005 відхиляється без округлення. ArithmeticException цієї конкретної перевірки перетворюється на українську IllegalArgumentException. Всі перевірки виконуються до присвоєнь.
- **Розглянуті альтернативи**: double дає похибки; округлення порушує clarify; перевірка лише scale <= 2 неправильно відхиляє кінцеві нулі; long суперечить UML.

## 3. Дати

- **Рішення**: LocalDate, навчальна дата звернення 2026-11-15, початковий строк 2026-12-15, продовження 2027-01-15 та 2027-02-15. Конструктор порівнює строк із фіксованою навчальною датою як локальним значенням, без нового параметра чи поля.
- **Обґрунтування**: приклад не залежить від дня запуску. extend порівнює новий строк із поточним і не змінює суму погашення.
- **Розглянуті альтернативи**: LocalDate.now робить приклади нестійкими; Clock та нова предметна сутність зайві й розширюють модель.

## 4. Відмови та void-операції

- **Рішення**: IllegalArgumentException для аргументів, IllegalStateException для недопустимої дії. За викрадення prepare спершу встановлює Rejected, потім кидає очікувану IllegalStateException; успішне повернення означає Ready. Інші відмови не змінюють дані. Стан після перевірки змінюється тільки після отримання boolean.
- **Обґрунтування**: виняток зупиняє шлях касира до хибного повідомлення про успіх, зберігаючи UML-сигнатури. Очікувані помилки перехоплюються лише біля відповідних негативних прикладів. Неочікувані помилки доходять до верхнього обробника, який друкує українське пояснення й завершує процес кодом 1.
- **Розглянуті альтернативи**: мовчазний return із void не дає касиру визначити успіх; boolean/Result змінює UML; власна ієрархія винятків зайва; перехоплення всіх RuntimeException приховує дефекти.

## 5. Доступ касира до приватних умов

- **Рішення**: пакетні getId, getPrincipal, getRepaymentAmount, getDueDate договору без setters. Окремо зіставити з атрибутами class, LoanAgreement!A3 та Cashier!A7 CRC.
- **Обґрунтування**: касир має показати фактичну позику й розрізняти запропоновану та належну суми. UML не містить методів читання цих даних. Доповнення зберігає private поля, усі задані члени та SRP. Це явний предмет майбутнього аудиту; недостатній відповідник означає розбіжність і заборону висновку про повну відповідність.
- **Розглянуті альтернативи**: відкриті поля порушують видимість; фінансовий друк у договорі — SRP; копії сум у касирі створюють два джерела істини; reflection у бізнес-коді невиправдана. Вихідні матеріали №1 не редагуються.

## 6. Тотожність, композиція та оцінювання

- **Рішення**: екземпляр Main зберігає набори створених і переданих id на весь запуск. Перевіряє їх до створення речі/договору, позначає передачу після успішного конструктора. Оцінювання закінчується до створення договору й після цього не викликається.
- **Обґрунтування**: реалізує два clarify без нового поля власника, блокувальних станів чи предметних класів. Викуп не знищує об'єкт. Незалежні звернення мають різні id.
- **Розглянуті альтернативи**: тотожність Java-посилань недостатня; статичний реєстр, поле власника та прапорець блокування оцінки зайві.

## 7. Перевірки

- **Рішення**: режими all, verify, fault-check. verify використовує явні перевірки й, за потреби, локальну reflection JDK для знімків приватних полів, без reflection у бізнес-операціях. Незавершену перевірку відтворює анонімний тестовий IStolenItemCheck, який кидає виняток; об'єкт зіставляється з умовою Draft у state та контрактом перевірки.
- **Обґрунтування**: перевіряється незмінність стану й даних без додаткових бізнес-getters, JUnit чи залежності від -ea. Окремий аварійний процес доводить припинення всього запуску.
- **Розглянуті альтернативи**: лише перегляд консолі не доводить незмінності; JUnit є зовнішньою залежністю; тестові прапорці в предметних класах розширюють модель.

Усі питання для планування вирішені. Фактична відповідність, зокрема технічних доповнень, доводиться після реалізації аудитом, а не цими проєктними рішеннями.

## Погоджене рішення I2 (2026-11-15)

Дозволено лише чотири пакетні методи читання LoanAgreement: `getId(): String`, `getPrincipal(): BigDecimal`, `getRepaymentAmount(): BigDecimal`, `getDueDate(): LocalDate`. Це погоджена технічна деталізація атрибутів, якої немає серед явно зображених операцій вихідної UML. Методи не змінюють стан і не додають правил, залежностей або відповідальностей; поля залишаються private, setters не додаються. Кожен метод зіставляється з однойменним атрибутом class, LoanAgreement!A3 та потребою Cashier!A7 у CRC. Буквальна тотожність переліків операцій не заявляється. Після реалізації перевірити й за потреби оновити окрему діаграму класів для звіту практичної №2 у `docs/practice2/class.mmd`, відобразивши фактичні методи та пакетну видимість.
