# Швидкий старт і перевірка майбутнього прототипу

**Задача**: 002 · **Дата**: 2026-11-15.

Це інструкція для етапу реалізації. Зараз Java-файлів і кореневого README ще немає; наведені результати є очікуваними. Компіляція та запуск на етапі планування не виконувалися.

## Передумови та робочий каталог

Потрібні JDK 17 або новіший із java та javac у PATH, Windows PowerShell і термінал, який відображає UTF-8. Залежності й доступ до мережі не потрібні. Команди виконуються з кореня репозиторію — каталогу, який містить src, docs і specs. Перейдіть до нього командою нижче, якщо використовуєте поточне розташування:

```powershell
Set-Location -LiteralPath 'C:\Users\pusto\Desktop\ооп\prak1\pawnshop'
java -version
javac -version
chcp 65001
[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)
$OutputEncoding = [Console]::OutputEncoding
```

Мову коду, типи й правила визначає [data-model.md](data-model.md); режими, канали, повідомлення й коди завершення — [contracts/console.md](contracts/console.md).

## Компіляція

Після появи запланованих вихідних файлів:

```powershell
New-Item -ItemType Directory -Force -Path out | Out-Null
javac --release 17 -encoding UTF-8 -d out src/pawnshop/*.java
$compileExitCode = $LASTEXITCODE
if ($compileExitCode -ne 0) { throw 'Компіляція прототипу завершилася помилкою' }
```

Очікування: код javac дорівнює 0, class-файли містяться в out/pawnshop. Мають бути скомпільовані всі десять вихідних файлів; зовнішній classpath не потрібен.

## Чотири демонстраційні маршрути

```powershell
java -Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -cp out pawnshop.Main all
$demoExitCode = $LASTEXITCODE
if ($demoExitCode -ne 0) { throw 'Демонстрація завершилася помилкою' }
```

Виклик без аргументу еквівалентний all. Перевірити чотири заголовки маршрутів і результати:

| Маршрут | Очікуваний результат |
| --- | --- |
| Оформлення → викуп | Оцінка 1000, позика 800, належить 840; Draft → Ready → Active → Redeemed; по одній видачі, імітації погашення й поверненню |
| Оформлення → два продовження → викуп | Дати 2026-12-15 → 2027-01-15 → 2027-02-15; до викупу Active, належить 840; лише одна видача |
| Викрадення | Локальний пошук id, Draft → Rejected; жодної виплати, погашення чи повернення |
| Некоректні дії | Передбачені відмови пояснені, дані й стан збережені; наступні незалежні приклади виконано |

За всіх очікуваних відмов запуск завершується кодом 0. Повторити all в новому процесі: початкові дані й результати однакові, немає накопичення попередніх договорів.

## Граничні перевірки

```powershell
java -Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -cp out pawnshop.Main verify
$verifyExitCode = $LASTEXITCODE
if ($verifyExitCode -ne 0) { throw 'Перевірки прототипу не пройдено' }
```

verify має використовувати явні перевірки, які не залежать від -ea. Кожна перевірка фіксує результат; невідповідність зупиняє запуск із ненульовим кодом. До й після відхиленої операції порівнювати потрібні поля й кількість успішних зовнішніх імітацій. Для недоступних полів дозволено reflection лише в перевірочній частині Main. Очікувані винятки перехоплюються біля конкретної спроби, не навколо всього маршруту.

| Група | Обов'язкові випадки та докази |
| --- | --- |
| Опис | null, порожній і пробільний опис відхилені до подання й договору; непорожній прийнятий |
| Оцінювання | Базовий appraise(item) записує й повертає 1000; перевантаження — явну допустиму суму. null/0/від’ємна/частки копійки перевіряються для перевантаження й setter зі збереженням попередньої оцінки. Відсутня річ відхиляється обома appraise. |
| Порядок оцінювання | Перегляд усіх сценаріїв підтверджує відсутність переоцінювання після конструктора договору |
| Умови договору | Без оцінки, borrower, item, checkService, строку чи сум чернетка не створена; appraisal=null блокує касира; початковий строк рівний/раніший за 2026-11-15 відхилений |
| Межі сум | principal=0 та principal>оцінки відхилені; principal=оцінки дозволений; repaymentAmount<principal відхилена, рівна дозволена |
| Точність усіх чотирьох сум | Для оцінки, principal, repaymentAmount, payment окремо перевірити цілі, .01, кінцеві .000 та відхилення .005 без округлення. Решта умов у кожному прикладі коректна: наприклад principal 800/800.01/800.000/800.005 при оцінці 1000; payment 840/840.01/840.000/840.005 при належних 840 |
| Перевірка викрадення | false → Ready, true → Rejected; контрольований виняток тестового сервісу залишає Draft. Після незавершеної перевірки activate відхилено без видачі |
| Порядок і повтори | prepare поза Draft відхилений; issueFunds до Ready та повторно з Active відхилений; викуп/продовження до Active відхилені |
| Викуп | На незалежних активних договорах 839 відхилено, 840 дозволено, 841 дозволено; запропоновану й належну суми розрізнено; null/0/від'ємний платіж відхилено; часткові платежі не накопичуються |
| Продовження | null, рівна та раніша дата відхилені; поточна+1 день дозволена; два послідовні продовження та наступний викуп успішні; principal/repaymentAmount незмінні, виплата не повторюється |
| Кінцеві стани | У Rejected та Redeemed окремо спробувати prepare, activate, redeem, extend: відмова, дані незмінні, немає повторних фінансових імітацій |
| Тотожність та композиція | Спроба створити іншу річ із тим самим id відхилена до створення; повторна передача речі у другий договір заблокована. Після невдалого конструктора договір не зайняв річ; наявні об'єкти не змінені |
| ООП і DI | final getId предка, override getRole трьох ролей через спільний тип, overload appraise, конструкторне DI; усі зв'язки відповідають class/CRC |

Вихідні виклики й переходи перевіряти разом із повідомленнями. Наявність рядка «успіх» без правильного стану та даних не є доказом.

## Контроль неочікуваної помилки

Окремий процес, який навмисно має завершитися невдало:

```powershell
java -Dfile.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -cp out pawnshop.Main fault-check
$faultExitCode = $LASTEXITCODE
if ($faultExitCode -ne 1) { throw 'Не підтверджено потрібний код аварійного завершення' }
```

Після службового повідомлення контролю помилки очікується українське пояснення у stderr, код 1, відсутність заголовків бізнес-маршрутів і загального підсумку успіху. Цей режим перевіряє той самий верхній обробник, що використовується для неочікуваних помилок звичайного запуску. За потреби окремо перевірити невідомий аргумент: українська інструкція, код 2, без сценаріїв.

## Чистий запуск за README та аудит

На етапі реалізації створити чистий тимчасовий каталог, скопіювати лише потрібні вихідні файли й документацію без out, виконати наведені команди за майбутнім README. Сам прототип запускається тільки javac/java; інструменти читання UML/CRC не є його залежностями. Записати фактичні команди, JDK, повідомлення, результати й коди завершення в model-code-review.md.

Аудит виконати за [plan.md](plan.md): усі типи/члени/виклики та службовий код у напрямку код → модель; усі п'ять документів і дев'ять CRC-карток у напрямку модель → код. Указувати точні місця й клітинки, окремо відповідності, розбіжності, неперевірені елементи. Перевірити всі вісім принципів конституції й контрольні суми захищених матеріалів. Жодного висновку про повну відповідність до усунення всіх розбіжностей і прогалин.

## Проміжне приймання

Після T020–T021 доступні verify та верхній обробник помилок: код 0 означає успіх лише реалізованого набору US1, який розширюється в US2/US3; код 1 — помилку. Повний контракт режимів завершується в US4. Це не приймання всього прототипу.

Ідентифікатори навчальних об’єктів — непорожні рядки без пробільних символів. null, порожній рядок і рядки з пробільними символами відхиляються. Порівняння точне, з урахуванням регістру, без обрізання пробілів або зміни регістру: I1 та i1 різні, повторне I1 означає ту саму річ у межах запуску.

Виявлення викрадення є винятком до незмінності стану після відмови. Після реалізації перевірити та за потреби оновити окрему `docs/practice2/class.mmd` для звіту №2 за правилом I2; оригінальні файли практичної №1 у docs/ незмінні.

**Межа дозволу N1**: `docs/practice2/class.mmd` — майбутній новий файл UML для практичної №2, відповідно до §VII конституції. Його створення передбачено після реалізації; під час поточного виправлення документації файл не створюється. Оригінальні `docs/class.mmd`, `docs/sequence.mmd`, `docs/state.mmd`, `docs/usecase.puml`, `docs/crc.xlsx` практичної №1 не редагуються. Захист наявних матеріалів docs/ не забороняє погодженого додавання цього нового файла №2.
